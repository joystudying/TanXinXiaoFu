# 语音链路与降级方案

回答两个问题：现在语音怎么走、能不能真双工、差电脑怎么办。

---

## 一、当前链路

```
老师的嘴 → 浏览器识别（Web Speech）→ 文字
                                    ↓
                          服务端 /api/chat
                                    ↓
              扮演学生的 DeepSeek → 文字回复
                                    ↓
             edge-tts 或浏览器朗读 → 老师听到
```

三个环节串行，一轮走完大约 **1.5–2.5 秒**（实测：模型 0.6–0.9 秒，合成 1.2 秒）。

### 这不算真双工

| 能力 | 现在 | 真双工 |
|---|---|---|
| 一直收音 | 否，说完才停 | 是 |
| 边说边理解 | 否，整句才发 | 是 |
| 边生成边出声 | 否，整段文字才合成 | 是 |
| 同时说和听 | 否 | 是 |
| 打断延迟 | 约 100–300ms（本地检测） | 约 100ms（服务端模型自己让路） |

**能补的和不能补的**：
- 能补：首响压到 1 秒、打断更快、边生成边念——这些都靠流式，不需要换服务。
- 不能补：两人同时说话时模型自己处理重叠。这必须有**端到端实时语音模型**。

## 二、真双工到底缺什么

缺一个服务，不是缺性能。

| 方案 | 中文 | 国内直连 | 真双工 | 需要什么 |
|---|---|---|---|---|
| 豆包实时语音（火山引擎） | 强 | ✅ | ✅ | APP ID + Access Token |
| 阿里百炼 Qwen-Omni | 强 | ✅ | ✅ | DASHSCOPE_API_KEY |
| OpenAI Realtime | 一般 | ❌ 要代理 | ✅ | OPENAI_API_KEY |

接进来之后架构变成：

```
浏览器 ⇄ 本服务 /ws/voice（代理，密钥只在这）⇄ 实时语音服务
   ↑
本地 VAD：一开口先把播放静音，不等服务端
```

`turns` 表照旧记录文字的转写结果，复盘的输入源不变。

## 三、差电脑怎么办：四档降级

**核心原则：客户端不跑任何模型。**

只有收音、放音、显示三件事。所以电脑性能差不该影响能不能用——
真正决定档位的是网络、浏览器、服务端配了什么。

| 档位 | 识别 | 合成 | 客户端负担 | 适用 |
|---|---|---|---|---|
| `full` | 服务端 | 服务端 | 最小 | 服务端装了 FunASR；任何电脑都行 |
| `hybrid` | 浏览器 | 服务端 | 小 | 默认档；Chrome/Edge |
| `lite` | 浏览器 | 浏览器 | 小 | 服务端没配合成时 |
| `text` | 无 | 无 | 最小 | 弱网、老浏览器、保底 |

### 自动选择逻辑

前端 `js/capabilities.js` 问服务端 `GET /api/capabilities`，
拿到「服务端现在有什么」，再结合本地三个信号：

```
网络是不是 2G/省流量  → 直接 text（语音一卡体验比文字还差）
服务端有识别+合成      → full
服务端只有合成         → hybrid（需要浏览器支持识别）
服务端都没配           → lite 或 text
```

不允许出现「选中了一档但跑不起来」——每一档都有下一档兜底。

### 为什么要测硬件

不是为了往上加功能，是为了**在低端设备上早点关掉重功能**。
`navigator.hardwareConcurrency` 和 `deviceMemory` 只用来做提示和选择档位，
不用来决定功能是否存在。

## 四、延迟预算

目标：老师说完到听见学生开口 ≤ 2 秒。

| 环节 | 现在 | 流式后目标 |
|---|---|---|
| 识别结束判定 | 1.2 秒静音判定 | 0.8 秒 |
| 模型首 token | 0.6–0.9 秒（整段返回） | 0.3 秒（流式） |
| 合成首包 | 1.2 秒（edge-tts） | 0.4 秒（按句合成） |
| 合计 | 约 2.4 秒 | 约 1.2 秒 |

流式改造后，**第一句话在 1 秒出头就能听见**，剩下的边生成边念。
观感上已经是"实时"，差别只在不能同时说话。

## 五、实施顺序

1. **流式输出**（不换服务，纯改造）
   DeepSeek 开 `stream=true`；按句切分，每句立刻送 TTS，边合成边播。
   预期首响 1.2 秒。
2. **持续收音 + 立刻打断**
   复用 `js/audio-capture.js`（16k PCM）与本地能量检测；
   开口即静音播放，延迟 <100ms。
3. **服务端识别（可选）**
   启动 `backend/services/funasr_server.py`，`ASR_PROVIDER=funasr`。
   好处：不挑浏览器、可离线。
4. **真双工（需要凭证）**
   接豆包或百炼，新增 `providers/realtime_xxx.py`，前端换成音频通道。
   前三步的代码全部复用，只换传输层。

前三步不需要任何新凭证。第四步才需要。

---

## 六、验收标准

完成第 1–2 步后，应满足：

- [ ] 老师说完到听见学生第一句 ≤ 1.5 秒（本机实测）
- [ ] 学生说到一半老师插话，播放停止 ≤ 200ms
- [ ] 弱网（3G）下自动切到文字，不出现卡住
- [ ] 老机器（4 核 4G）能完成一整轮对话
- [ ] 断网时给出明确提示，不是一直转圈

完成第 4 步后追加：

- [ ] 双方同时说话时，学生不会把老师的声音识别成自己的
- [ ] 老师插话后，学生的回应基于最新内容而不是上一句

---

## 七、给接手的人

- 想改音色：`TTS_VOICE` 换名字即可；要"某个特定人的声音"需要声音克隆，那要 GPU 或云服务。
- 想换识别：`providers/` 加一个实现，`ASR_PROVIDER` 改一行。
- 想加速度：先做第五节的第 1 步，收益最大、风险最低。
- 想真双工：先确认有没有实时语音服务的凭证，没有就先做前三步。
