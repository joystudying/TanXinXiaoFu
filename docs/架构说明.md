# 架构说明

改代码之前读这一份。它回答三个问题：东西在哪、为什么这样分、动了会坏什么。

---

## 一、全景

```
浏览器（原生 HTML + JS，无构建）
  │  文字：POST /api/chat        语音：WebSocket /ws/chat
  ▼
FastAPI
  ├── api/         校验参数，转手给 services
  ├── services/    业务：角色设定、守卫、一轮对话编排
  ├── providers/   外部能力：模型、识别、合成（唯一发 HTTP 的地方）
  └── db/          建表 + 全部 SQL
        │
        ▼
     SQLite（cases / sessions / turns / request_log）
```

外部依赖只有三个，都在 `providers/` 后面：

| 环节 | 当前默认 | 换的方法 |
|---|---|---|
| 扮演学生的大模型 | DeepSeek | 新增 `providers/llm_xxx.py` |
| 语音识别 | 浏览器自带 / FunASR | 新增 `providers/asr_xxx.py` |
| 语音合成 | edge-tts | 新增 `providers/tts_xxx.py` |

## 二、分层与边界

这是硬规矩，`scripts/check_boundaries.py` 会自动检查。

| 层 | 可以做 | 不可以做 |
|---|---|---|
| `api/` | 参数校验、调用 services、组装响应 | 写 SQL、直接 import httpx |
| `services/` | 业务逻辑、调用 providers 与 db | 写 SQL、直接发 HTTP |
| `providers/` | 调外部服务、协议适配 | import `db`（厂商层不碰数据） |
| `db/` | 建表、所有 SQL | import `services` |

**为什么这么严**：一条链路上有四个能写 SQL 的地方，三个月后没人知道哪段代码改了数据。
现在换数据库只改 `db/` 一个目录，换厂商只改一个文件。

### HTTP 只有一处

`providers/` 是全项目唯一允许 `import httpx` 的地方。
业务层想调外部服务 → 写一个 Provider 实现类，不要在 service 里直接 requests。

## 三、一次对话的完整链路

### 文字（REST）

```
POST /api/chat {session_id, text, idempotency_key}
  → api/chat.py            参数校验
  → turn_engine.run_turn() ──┬→ repo.begin_turn()   事务内：查 pending、占幂等键、分配轮次、写入老师这句
                             ├→ persona.build_messages()  案例 → system prompt
                             ├→ guard.looks_like_injection()  加一条防守提示
                             ├→ model.call_model()  调大模型
                             ├→ guard.leaks_private()  检查输出有没有说出隐藏设定
                             └→ repo.finish_turn()  写学生这句、缓存响应
  ← {turn_no, reply_text, usage, latency_ms, degraded}
```

### 语音（WebSocket）

```
WS /ws/chat
  ← {"type":"ready", session_id, student_name, asr, tts}
  → {"type":"text","text":"…"}      ┐
  → {"type":"audio","audio_b64":…}  ┼→ 同一个 run_turn()
  → {"type":"reset"}                ┘
  ← {"type":"reply", text, turn_no, audio_b64, audio_format}
```

**关键**：两个端点共用 `run_turn()`。
幂等、失败回滚、泄漏检查、落库的行为完全一致，有测试专门守着这条。

## 四、数据模型

| 表 | 作用 | 关键字段 |
|---|---|---|
| `cases` | 虚拟学生案例 | `public_json` 老师能看的；`private_json` 隐藏设定，永不出接口 |
| `sessions` | 一次训练 | `status`：created → active → ended |
| `turns` | 每一句话 | `turn_no` 从 1 递增；老师偶数前、学生偶数后（1/2、3/4…） |
| `request_log` | 幂等记录 | `idempotency_key` 唯一；`status`：pending / done / failed |

### 幂等怎么工作

前端每次说话生成一个 UUID，重试时复用同一个。

1. `begin_turn` 在**写事务**里先查本会话有没有 `pending` —— 有就 409，防止并发重复。
2. 插入 `request_log`；键冲突时看 `request_hash`：
   - 一样且已完成 → 直接返回上次的结果（不重复调模型）
   - 一样但之前失败 → 重置为 pending，允许重试
   - 不一样 → 422，说明同一个请求号被用了不同内容

**为什么老师那句要先写进去再删**：这样 `turn_no` 的分配天然互斥，
模型调用期间不会持有写锁（模型可能要 20 秒）。

## 五、Provider 契约

新增实现只要满足这三个接口（`providers/base.py`）：

```python
class LLMProvider(ABC):
    async def chat(self, messages: list[dict], *, json_mode: bool = False) -> LLMResult

class ASRProvider(ABC):
    async def transcribe(self, audio: bytes, audio_format: str = "pcm16") -> str

class TTSProvider(ABC):
    async def synthesize(self, text: str) -> TTSResult
```

失败时抛 `providers.base` 里的异常：

| 异常 | 含义 | 上层怎么处理 |
|---|---|---|
| `ProviderTimeout` | 超时 | 504，提示可重试 |
| `ProviderRejected` | 4xx（密钥错、参数错） | 502，提示检查配置，不重试 |
| `ProviderError` | 其他失败 | 502，提示稍后重试 |

```python
@dataclass
class LLMResult:
    text: str
    usage: dict = field(default_factory=dict)
    emotion: str | None = None    # 留给将来的情感语音

@dataclass
class TTSResult:
    audio: bytes
    format: str = "mp3"
```

## 六、WebSocket 协议

客户端 → 服务端：

| 消息 | 字段 | 说明 |
|---|---|---|
| `text` | `text` | 文字一轮 |
| `audio` | `audio_b64`, `audio_format` | PCM16/16k/单声道，服务端识别 |
| `reset` | — | 结束当前会话，开新的 |

服务端 → 客户端：

| 消息 | 字段 | 说明 |
|---|---|---|
| `ready` | `session_id`, `student_name`, `scenario`, `asr`, `tts` | 连上就有 |
| `reply` | `text`, `turn_no`, `audio_b64`, `audio_format`, `degraded` | 一轮结果 |
| `error` | `code`, `message`, `retryable` | 出错，连接不关 |
| `reset` | `session_id` | 回应 reset |

音频上限 4 MB 一次，超了直接拒绝（防误传大文件撑爆内存）。

## 七、错误码

前端 `ERROR_TEXT` 表里逐条对应人话，改错误码记得同步。

| code | HTTP | 含义 | 可重试 |
|---|---|---|---|
| `session_not_found` | 404 | 会话不存在 | 否 |
| `session_closed` | 409 | 训练已结束 | 否 |
| `duplicate_in_flight` | 409 | 上一句还在处理 | 是 |
| `idempotency_mismatch` | 422 | 同请求号不同内容 | 是 |
| `rate_limited` | 429 | 说太频繁（60 秒 10 次） | 是 |
| `model_timeout` | 504 | 模型超时 | 是 |
| `model_unavailable` | 502 | 模型不可用 | 看情况 |
| `asr_no_speech` | — | 没识别到内容 | 是 |
| `asr_unavailable` | — | 识别服务挂了 | 是 |

## 八、几个决定的理由（避免后来人重复讨论）

**为什么 REST 和 WebSocket 同时存在**
REST 好调试、好重试、能幂等；WebSocket 省握手、能传音频。
两个都留着，业务逻辑抽在一处，代价只有一层转发。

**为什么没换成 SQLAlchemy**
合作方用的是 SQLAlchemy 单表。换过去要丢掉会话状态机、幂等、四表关系和 42 条测试。
收益是"能切 PostgreSQL"，但当前没有多实例需求。将来真要多实例再单独评估。

**为什么模型调用不用 openai SDK**
规定"只有一个 HTTP 出口"。引入 SDK 后边界检查就失效了，而且多一个依赖。

**为什么语音识别放在浏览器**
零安装、零延迟、不用部署。代价是只支持 Chrome/Edge 且要联网。
需要全覆盖时启动本地 FunASR 即可，前端不用改。
