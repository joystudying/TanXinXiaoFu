# 实时语音（真双工）选型

> 结论先说：**现在的"识别→模型→朗读"三段拼接做不到真双工**，换音色也没用。
> 真双工需要端到端实时语音模型——音频进、音频出、模型自己处理打断。
> 这件事卡在一个东西上：**实时语音服务的凭证**。目前项目只有 DeepSeek（纯文本）。

---

## 一、为什么现在的方案到不了

现在这条链是：

```
浏览器识别（Web Speech） → 文字 → DeepSeek → 文字 → edge-tts → mp3 → 浏览器播放
```

四个环节串行，且被"轮"切开：

| 环节 | 现在的状态 | 真双工要求 |
|---|---|---|
| 收音 | 一轮说完才结束 | 一直开着，边说边出字 |
| 理解 | 拿到整句才发请求 | 边说边理解，可被打断 |
| 回应 | 等模型吐完整段文字 | 边生成边出声，首包 <500ms |
| 打断 | 靠能量检测事后停播 | 模型侧感知重叠语音并自己让路 |

三个硬伤：**首响 2 秒以上**、**不能同时说和听**、**打断有延迟**。
把 TTS 换成 edge-tts 只解决"音色自然"，解决不了这三个。

## 二、三条真双工路线

| | 豆包实时语音（火山引擎） | 阿里云百炼 Qwen-Omni 实时 | OpenAI Realtime |
|---|---|---|---|
| 形态 | 端到端语音大模型，WebSocket | 端到端语音模型，WebSocket | 端到端实时，WebRTC/WS |
| 中文效果 | 强，原生中文 | 强 | 一般，中文不如前两家 |
| 打断 | 原生支持 | 支持 | 原生支持 |
| 首响 | 约 500–800ms | 约 600–900ms | 约 400–700ms |
| 国内网络 | 直连 | 直连 | **需代理**，直连不通 |
| 声音定制 | 支持声音复刻 | 有限 | 有限 |
| 计费 | 按音频时长 | 按 token/音频 | 按音频时长，最贵 |
| 需要给我 | APP ID + Access Token | DASHSCOPE_API_KEY | OPENAI_API_KEY |
| 现有代码改动 | 大（换掉整套对话链路） | 大 | 大 |

三家都要**换掉现在的"演员"**：现在的学生人设是喂给 DeepSeek 的一段 system prompt，
换成端到端语音模型后，人设要写进它的会话指令里，对话历史也由它维护。
这意味着 `/api/chat` 那条链路会被绕开，M2 做的幂等、轮次落库要重新对接到音频会话上。

## 三、我的建议

**优先豆包**，理由三条：

1. 原生中文，语音自然度最接近真人；
2. 国内直连，不用代理，延迟稳定；
3. 支持声音复刻——小陈、小许、小周可以各配一个固定音色，比随机选音色真实得多。

备选阿里云百炼：如果你们学校已有阿里云账号，走这条更省事。

## 四、落地后架构会变成

```
浏览器 ──PCM16 16k 音频流──► 本服务 /api/voice/realtime（WS 代理）
                              │  key 只在这里
                              ▼
                        豆包实时语音 WS
                              │
浏览器 ◄──音频流 + 转写事件────┘
          ↑
     本地 VAD：一开口就把播放静音（<100ms），不等服务端
     文字同时落库，复盘的输入源不变
```

保留的部分：会话/案例/轮次落库、幂等、人设文案、复盘链路——这些和语音无关。
替换的部分：`speech.js` / `speak.js` / `vad.js` → 一个音频通道 + 事件处理。

## 五、需要你提供

一个凭证，二选一：

- 火山引擎：实时语音大模型的 `APP ID` 与 `Access Token`（控制台 → 语音技术 → 实时语音）
- 阿里云百炼：`DASHSCOPE_API_KEY`

拿到之后我先做**单条通路验证**：浏览器说一句话，看能不能拿到音频回包和转写。
验证通了再接 UI，不通就换另一家——避免大改完发现用不了。
