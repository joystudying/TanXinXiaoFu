# 合作仓库对比（2026-10-31）

对比对象：
- 合作方：`github.com/joystudying/TanXinXiaoFu`（公开，1 个提交，6.5 MB）
- 我们：`D:\tanxin` / `github.com/lovezexiaoze/tanxin`（私有，5 个里程碑）

**一句话结论**：合作仓库在「语音链路」和「厂商解耦」上领先，我们在「数据严谨性」和「可验证性」上领先。
两边功能互补，拼起来才是完整产品；现在合并比各做各的划算。

---

## 一、最大区别：通信模型不一样

| | 合作仓库 | 我们 |
|---|---|---|
| 通道 | **WebSocket `/ws/chat`** 长连接 | **REST `/api/chat`** 每轮独立请求 |
| 会话状态 | 存在服务端内存 `SessionState` | 存数据库（`sessions` 表 + 状态机） |
| 幂等 | 无 | 有（同 key 不重复调模型、不重复写轮次） |
| 并发 | 未处理（同一 WS 串行天然安全） | `BEGIN IMMEDIATE` 会话级串行 |
| 失败处理 | 无（异常直接断连） | 超时/失败回滚老师那句，不留半轮 |

他们的 WS 方案天然串行，因此不需要幂等；我们的 REST 方案需要。
**这不是谁对谁错，是取舍**：WS 简单但断线即丢状态，REST 可重试但要做幂等。

## 二、他们领先的地方（建议直接吸收）

### 1. Provider 抽象层（最有价值）

```
app/providers/
  base.py          ASRProvider / LLMProvider / TTSProvider 三个接口
  asr_funasr.py    本地 FunASR 客户端
  asr_stub.py      未接入时的占位
  llm_deepseek.py  DeepSeek 实现
  tts_edge.py      edge-tts 实现
  tts_stub.py      不发声占位
  __init__.py      build_providers() 按 .env 装配
```

换厂商只改 `.env` 里的 `ASR_PROVIDER` / `TTS_PROVIDER` / `LLM_PROVIDER`，业务代码一行不动。
我们现在的 `services/model.py` 写死了 DeepSeek，换厂商要改代码——这条必须学。

### 2. 本地 FunASR（真离线识别）

`backend/services/funasr_server.py` 是独立进程（端口 8001），用阿里开源的 paraformer-zh 模型，
首次运行自动下载约 1 GB。特点：**离线、免费、中文识别强**。

这正好解决"识别依赖云、断网就废"的问题，也比浏览器 Web Speech 更可控（不挑浏览器）。

### 3. 部署配置

- `tools/caddy/Caddyfile`：静态页 + `/ws/chat` 反代，监听 5180
- `cloudflared` 隧道：手机/公网测试
- **关键**：手机浏览器要求 HTTPS 才能用麦克风，这条我们整个缺失。

### 4. 前端 UI 更新版

他们的 `styles.css` 63.6 KB，我们的 62.2 KB；`conversation.html` 他们 7.0 KB（含文字兜底内联样式 + voice.js），我们 4.9 KB。
**他们手上的 UI 版本比我们那个 zip 更新**，我们应该以他们的为准。

## 三、我们领先的地方（建议他们吸收）

| 项 | 我们的做法 | 他们 |
|---|---|---|
| 数据模型 | `cases / sessions / turns / request_log` 四表，案例含 public/private 分离 | 只有 `turns` 一张表，角色硬编码在 `ws/chat.py` |
| 幂等 | 同 key 重试不重复调模型、不重复写 | 无 |
| 私有设定防护 | 私设只进 system prompt + 注入检测 + 输出黑名单 + 20 条泄漏用例 | 私设只在服务端（有），但无输出检查 |
| 测试 | 35 条 pytest（会话/对话/幂等/超时/守卫/关闭） | 无 |
| 架构守卫 | `scripts/check_boundaries.py`（分层越界自动报错） | 无 |
| 过程资产 | 设计文档 + 技术路径 + 决策记录 + CHANGELOG，git 打了 5 个标签 | 单条 README |
| 音频采集 | AudioWorklet（独立线程） | ScriptProcessor（主线程，已废弃，会有卡顿） |

其中**测试和边界检查**是最该同步过去的——他们现在改代码没有任何自动回归。

## 四、冲突点（合并前必须先定）

| 冲突 | 选项 A | 选项 B | 建议 |
|---|---|---|---|
| 通道 | 统一 WS | 统一 REST | **REST 保稳 + WS 作语音通道**，两条并存 |
| 数据库 | SQLAlchemy async | 裸 sqlite3 | **迁到 SQLAlchemy**（他们已有，还能切 PG） |
| 会话状态 | 内存 | 落库 | **落库**（断线可恢复、能复盘） |
| 前端语音 | voice.js（WS + PCM16） | 我们的 speech/speak/vad | **取双方优点**：WS 通道 + 我们的 VAD 打断与朗读降级 |

## 五、建议的合并路线

**阶段 1（1 天）· 以他们为骨架**
拿他们仓库当基底（provider + WS + FunASR + Caddy），把我们这四样移植进去：
- `db/schema.sql` 四表 + `repo.py` 的幂等/事务逻辑
- `services/persona.py` + `guard.py`（私设组装与输出检查）
- `tests/` 35 条 + `scripts/check_boundaries.py`
- `docs/` 全套

**阶段 2（1 天）· 前端合并**
取他们更新的 UI + `voice.js` 的 WS 通道，把我们 `vad.js`（开口打断）、`speak.js`（音色挑选）、
`pcm-worklet.js`（AudioWorklet 采集）替换掉 ScriptProcessor。

**阶段 3（0.5 天）· 跑通离线链路**
启动 FunASR 服务 → 关掉外网 → 验证"断网也能对练"。

**阶段 4 · 再谈真双工**
本地 FunASR + 流式 LLM + 流式 TTS 已经能把首响压到 1 秒内，
比换端到端语音模型便宜得多，也更可控。真双工最后再评估。

## 六、风险提示

1. **两边都在改同一批文件**（`conversation.html`、`styles.css`），直接覆盖会丢改动。
   合并前先各自提交、再在一个分支上合，别裸拷贝。
2. 他们的 `frontend-html/` 目录名和我们 `frontend/` 不同，合并时统一目录名，否则部署脚本要改。
3. FunASR 需要 **Python 3.10/3.11**，主后端要 3.11+，他们已提示"单独建环境不要混用"——这条必须遵守。
4. 他们仓库是**公开**的，里面有学生角色设定样例。虽然都是虚构人物，正式接入真实案例前要确认仓库可见性。
